# CoachPulse frontend/backend integration

## Local development without Docker

### PostgreSQL

Install PostgreSQL for Windows using the official installer, start the PostgreSQL service, then open SQL Shell (`psql`) and create a local role and database:

```sql
CREATE ROLE coachpulse LOGIN PASSWORD 'replace-with-a-local-password';
CREATE DATABASE coachpulse OWNER coachpulse;
```

From the repository root, store the connection string and development JWT settings in .NET user-secrets. This generates a local signing key at command time; it does not write it to the repository:

```powershell
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Host=localhost;Port=5432;Database=coachpulse;Username=coachpulse;Password=replace-with-a-local-password" --project CoachPulse.Api
dotnet user-secrets set "Jwt:Key" ([Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(48))) --project CoachPulse.Api
dotnet user-secrets set "Jwt:Issuer" "CoachPulse.Api" --project CoachPulse.Api
dotnet user-secrets set "Jwt:Audience" "CoachPulse.Client" --project CoachPulse.Api
```

Apply migrations explicitly; the application does not migrate the database automatically:

```powershell
dotnet ef database update --project CoachPulse.Infrastructure --startup-project CoachPulse.Api
```

The API exposes `/healthz` as process liveness. `/readyz` returns 503 until PostgreSQL is reachable, migrations are current, and seeding plus recurring job registration complete. A pending migration is reported in the API log and readiness payload. Startup does not hide database errors or report readiness early.

Start the API on the Vite proxy target:

```powershell
dotnet run --project CoachPulse.Api --launch-profile http
Invoke-RestMethod http://localhost:5006/healthz
Invoke-RestMethod http://localhost:5006/readyz
```

In local development, Hangfire's server and dashboard are disabled by default so a stopped PostgreSQL instance cannot prevent the API's liveness endpoint from starting. When PostgreSQL is available and recurring jobs/dashboard are needed locally, enable them in user-secrets and restart:

```powershell
dotnet user-secrets set "Hangfire:RunServer" "true" --project CoachPulse.Api
dotnet user-secrets set "Hangfire:EnableDashboard" "true" --project CoachPulse.Api
```

The dashboard still enforces the SuperAdmin authorization filter. Production enables the server and dashboard by default and must have PostgreSQL available at startup.

### Frontend

```powershell
Set-Location CoachPulse.Frontend
Copy-Item .env.example .env.local
npm install
npm run dev
```

The example leaves `VITE_API_BASE_URL` and `VITE_HUB_BASE_URL` empty. Vite proxies `/api`, `/hubs` (including WebSocket upgrades), `/healthz`, and `/readyz` to `http://localhost:5006`, avoiding development CORS. `.env.local` is ignored by Git. The repository root `.env` is not loaded by `dotnet run`; do not copy secrets from it into tracked configuration.

## Contract and inventory

The source of truth is `docs/swagger.json`; generated TypeScript declarations are in `CoachPulse.Frontend/src/api/generated.ts`. Regenerate with `npm run generate:api-types` from the frontend directory. The method-by-method call-site scan is `docs/FRONTEND_ROUTE_INVENTORY.md`, generated by `npm run inventory:routes`.

The current Swagger has 218 operations. The latest scan finds 201 frontend call sites and zero active operations without a matching frontend workflow. Sixteen deprecated compatibility operations use their canonical route in the UI; the Paymob provider webhook is intentionally backend-only. A call-site match does not prove that a UI flow works against a live API. `docs/API_INTEGRATION_AUDIT.md` contains the operation-level classification and can be regenerated with `npm run audit:api`.

## Implemented integration work

- Vite + React Router remain the frontend; unused Next app/config files and dependencies were removed after checking there were no Next imports.
- Generated OpenAPI types and a shared API client provide bearer auth, one-at-a-time refresh-token rotation, `ApiError` from ProblemDetails, `Retry-After`, idempotency keys, multipart upload, and authenticated blob downloads.
- Added screens/actions cover client progress and program history, Check-in detail/review, invitation resend/cancel, chat deletion/unread count, notification read/delete, program exercises and mutations, plan edit/archive, coach team and assigned-client view, tenant branding, SuperAdmin tenant lifecycle/usage, and global exercise CRUD/CSV import. Account data export/file actions, invoices, AI draft review, payment insights, and subscription lifecycle actions are also connected. DTO bodies are taken from generated Swagger schema types where a request body is used.
- Paymob checkout now returns a hosted Unified Checkout `checkoutUrl`; the API secret is not returned. The intention client secret appears only as a required short-lived URL parameter, is not logged, and is held in Data Protection-protected idempotency snapshots. The browser redirects to Paymob, then polls the owned payment status for up to two minutes. See `docs/PAYMOB.md` for dashboard Return/Webhook URLs and local tunnels.
- Notifications now have unread filtering, pagination, per-record read/delete actions, preferences, and SignalR refresh. Client chat uses ChatHub typing/presence and invokes `MarkAsRead` with REST fallback.
- Added `docs/FRONTEND_UNLINKED_ENDPOINTS.md`; active API operations have screens/actions, the Paymob webhook is backend-only, and deprecated aliases are intentionally not linked.
- Existing screens connect to core auth/account, tenant/client, invitation, program/exercise/meal-plan, check-in/files, subscription/payment, notification, chat/SignalR, AI, analytics, audit, and SuperAdmin flows. The audit lists every remaining operation; matching a request in the UI is not considered proof of end-to-end behavior.
- The API now initializes seed data and recurring jobs after the application starts. Liveness can start without PostgreSQL; readiness remains false until the database is migrated and initialization succeeds. Development Hangfire can be enabled through user-secrets. The Hangfire dashboard is omitted from the development pipeline by default because its middleware initialization requires the Hangfire store.
- Added API, AI, and web Dockerfiles, private/public compose networks, one-shot migrator, Caddy proxy, health checks, persistent uploads/Data Protection keys, and a production compose overlay. The local Compose stack is running at `http://127.0.0.1:8088`; `/healthz` and `/readyz` both returned 200, with database, startup initialization, and Python AI ready. `docker compose ps` showed no host-published port for the AI service.
- Fixed a runtime DI ambiguity in `TenantController`, allowed an unassigned Draft program to be created before its explicit assignment, and fixed ChatHub tenant queries that had inherited an unset request-scoped tenant filter. The latter was found by the authenticated SignalR E2E journey.

# Workspace approval and demo content

Workspace registration now creates a `PendingApproval` request and returns HTTP 202 without issuing access or refresh tokens. SuperAdmins review requests in the platform dashboard and approve with a required reason. Approval changes the tenant to `Active`; only then can its owner sign in or clients discover/join it. See the workspace onboarding section in `README.md`.

The Development demo seeder includes representative records across core screens. Enable it with `DemoSeed__Enabled=true` and set `DemoSeed__Password` outside Git. It never runs in Production; existing databases with the `coachpulse-demo` tenant are left untouched so rerunning startup cannot duplicate or overwrite demo records.
